# 周月报

作者：jiaqi ding

用自然、具体的中文整理实际工作，生成可直接复制的周报或月报。默认只在会话中输出正文，不创建文件、修改项目状态、发布页面或发送报告。用户明确要求保存时再按指定位置和项目约定写入。

## 周报：范围与时间

- 默认范围是当前项目及其下面的全部子项目，不因存在子项目而缩小范围；用户明确指定目录、项目或事项时按指定范围。结合工作目录、会话和项目入口确定当前项目，不能仅因 Git 仓库根目录更大就扩大范围。
- 先读项目入口和适用的 AGENTS.md，识别子项目、状态记录和日志位置。涵盖范围内各子项目的工作，但不要求通读全部文件。用时间和任务线索定位相关材料，不进入无关的相邻项目。
- 用户未指定时间时，按北京时间取上一个完整自然周，即上周一 00:00 至本周一 00:00（不含）。报告周期放在正文之前单独说明，不放进可复制正文的标题或条目。周日发起时也取此前一周，不把本周当成上周。
- 用户指定时间时优先遵循；只有时间表述确实无法判断且影响内容归属时才询问。

## 周报：取材与归纳

读取范围内的状态文件、工作日志、相关成果文档和 Git 提交记录，并纳入当前会话中用户补充的工作。Git 用于补充时间和变更证据，未提交工作及沟通、运维等事项也可以纳入，不能把提交列表直接当成工作清单。

- 按工作实际发生时间归入报告周期。文件修改时间、文档当前状态或一次提交不能单独证明所有内容均在当周完成；历史累计数据不能写成当周新增。
- 先识别当周涉及的各项工作，再围绕动作、结果和必要边界归纳。对同一事项的多次开发、修复、复测合并表达，保留能说明实质进展的步骤。
- 项目记录中的计划、建议和待办不能写成完成事项。明确区分开发完成、离线验证、真实服务验证、本机可用、服务器部署和生产上线。
- 数字保留必要的样本、范围、日期或比较口径；核验数量与准确率、开发案例与生产效果分别表述。不为报告重新运行大规模实验或访问生产服务。
- 用户补充的事实可以直接使用；与项目记录存在实质冲突时，核对相关证据，仍不能解决则简短指出或询问，不猜测补齐。
- 当周证据不足时只写可确认事项；完全没有可确认工作时说明缺少哪些记录，不将旧成果移到本周，不以“无记录”断言“未开展工作”。

## 周报：格式与摘要分工

技术项目默认采用用户确认的格式：正文放在 `text` 代码块中，一行项目分类标题，末尾使用半角冒号 `:`，随后是 `1.执行者摘要` 和 `2.技术摘要`。标题和节名顶格，每条要点独占一行，以两个空格及 `- ` 开头，不手动折行；同一项目内标题、节名和条目之间均不插入空行。不额外添加“周报”总标题或多级章节。报告周期在代码块之前单独说明。

标题沿用已有分类和真实项目名称，例如 `编程工作-科研项目-河湖遥感图斑AI辅助研判:`；其他项目按实际类别命名，不机械套用“编程工作-科研项目”。多项目在同一代码块内分别组织，项目之间空一行，普通非技术事项可直接列要点。

- 执行者摘要给领导阅读，通常归纳为3条，每条采用“主题：结果”的短句。说明做成了什么、可用到什么程度、主要工作量或效果及关键限制；保留少量能判断进展的数字。省略模型型号、token、参数档位、接口协议、测试文件及故障处理过程等实现细节，让读者只读这一节也能理解项目进展。
- 技术摘要给需要实现依据的读者阅读，通常4—6条，每条1—2句。按工作主题合并主要实现、数据规模、验证结果和部署状态，保留能解释结果的技术细节；不复述排查流水或罗列每轮实验。测试数量、性能指标和版本只在能说明保障、收益或边界时保留。
- 两节按受众重新归纳，不逐条换词重复。执行者摘要可将多个技术事项合并为一个成果；技术摘要补充实现与证据。数字和完成状态必须一致，必要限制就近说明，不在每条反复加同一免责声明。
- 默认采用精简版：每条围绕一个实质进展，删除背景铺垫、重复解释和次要数字。不为凑条数拆分事项，也不为压缩篇幅删掉关键失败或未完成边界。

格式示意（占位内容不作为工作事实）：

```text
工作类别-项目类别-项目名称:
1.执行者摘要
  - 流程更新：完成哪些调整，已供谁使用。
  - 应用进展：完成什么能力，取得多少有效结果。
  - 阶段验证：验证范围与结果，尚未完成的关键环节。
2.技术摘要
  - 完成某项实现。补充处理范围、实现要点和验证结果。
  - 完成某项应用。说明数据接入、实际运行及交付情况。
  - 开展对照验证。保留关键指标、样本口径及未决问题。
```

## 月报：根据用户提供的周报汇总

月报以用户提供的当月周报文字为依据，支持多项目内容。缺少周报正文时请用户提供；默认不从当前项目自行生成月报，也不拿周报参考示例充当当月事实。用户明确要求结合项目记录时才扩展取材。

- 按实际内容归纳栏目，使用“（一）……相关工作”等自然分类；预算项目、科研项目、地图服务等仅是可能的分类，不是固定栏目。
- 同一事项跨周反复出现时合并为本月进展，保留主要动作和截至材料末期的结果，不逐周罗列，也不把阶段数量简单累加。仅在增量和范围明确、互不重叠时合计数字。
- 从提供的材料确定所属月份；无法确定且影响归属时询问。跨月周报只纳入能确认属于目标月的事项，不自行拆分无法确定日期的数量或成果。
- 提供的周报不完整时，可以基于现有材料汇总，并在正文之外简短注明覆盖限制，不虚构缺失周的工作。
- 月报以简洁事项为主，突出本月实质工作；保留关键结果及必要的未完成边界，压缩底层实现细节，不强行采用周报的两层结构。

## 文风与交付检查

- 正文不使用 Markdown 加粗。允许标题、编号和项目符号，避免表格和过多层级影响复制使用。
- 直接写真实动作、对象和结果，不使用宣传口号、空泛评价、翻案句或生造术语。不将“编写文档”“提交代码”等过程自动拔高成业务成效。
- 保留准确的业务名称和必要技术术语；执行者摘要和月报优先使用读者能理解的表达。不额外添加用户未要求的下周计划、风险清单或工作建议。
- 检查日期与项目范围、重复事项、数字口径、完成状态和未证实内容。检查与材料规模相称，不为写报告改动程序或重跑测试。
- 最终将可复制的报告正文放在 `text` 代码块中输出；月报保留其栏目结构，不强套周报两层摘要。报告周期、必要的材料限制或待确认项放在代码块之外简短说明；不附冗长的取材过程、证据清单或未经要求的引用。
